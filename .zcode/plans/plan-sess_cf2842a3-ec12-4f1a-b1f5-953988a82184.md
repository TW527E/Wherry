## 目標
把「指令車道」與「重工作車道」拆開，並把收集/發布背景化，讓 Telegram 指令與按鈕能即時反應，不再排在數十秒的 X 掃描後面。並發安全靠既有的 SQLite 交易 + `claimJob()` 原子認領 + 批次狀態檢查保證（這些已存在），不引入 worker_threads。

## 根因（已查證）
- `src/lifecycle.ts` 的單一全域 `SerialWork` FIFO 佇列，把重工作（collect→seal→worker.run，數十秒）和輕指令（毫秒級 SQLite 讀寫）串在同一條排隊線上（`app.ts:106/118/136`）。指令因此得等在途收集跑完。
- `getUpdates` 用 `timeout: 0`，每 5 秒才輪詢一次（`telegram.ts:94`、`app.ts:165`），閒置時也有最多 5 秒延遲。
- `Engine` 無可變記憶體狀態（全 `readonly`），`Worker` 只有 `stopping`/`active` 單飛旗標 → 拆車道不會產生記憶體競爭。

## 實作方案

### 1. 雙序列車道（`src/lifecycle.ts` + `src/app.ts`）
- 保留 `SerialWork`，在 `createRuntime` 建立兩個實例：
  - `heavy`：跑 `runCycle`（collect→seal→worker.run）。
  - `control`：跑 Telegram callback / command / reminder reply / session upload。
- 把 `app.ts:106/118/136` 的 `serial.run(...)` 改成 `control.run(...)`；`runCycle`（`app.ts:88`）改用 `heavy.run(...)`。
- `stop()`（`app.ts:177-183`）改為 `await Promise.allSettled([cycle, commands, menu])` 後 `await heavy.drain(); await control.drain();`。

### 2. 收集背景化（`src/app.ts`）
- `runCycle` 已有單飛守衛 `if (cycle) return cycle;`（`app.ts:87`），本來就不會並行兩次收集 —— 拆到 `heavy` 車道後，指令車道不再被它擋住，收集自然變成背景工作。
- `/sync`（`app.ts:131-135`）目前 `await once()` 會讓使用者等整個收集鏈。改為：觸發 `void once()`（背景啟動，沿用單飛守衛），立即回覆「已開始檢查，結果請看 /status」，不阻塞指令車道。

### 3. approve 後立即發布（配合既有 review-notice 進行中工作）
- approve/callback 在 `control` 車道呼叫 `engine.action('approve', id)` 後，用 `void worker.run()` 觸發背景發布（`worker.run()` 既有單飛守衛 `app.ts` `Worker.run`，會安全併入在途 run 或啟動新的），不阻塞回覆。

### 4. Telegram 長輪詢（`src/platforms/telegram.ts` + `src/app.ts`）
- `getUpdates` 的 `timeout: 0` 改為 `timeout: 25`（真正 long-poll），並把 HTTP `timeoutMs` 放寬到 > 25s（透過 transport options）。
- `commandCycle` 的輪詢間隔（`app.ts:165` 的 `every(5000, ...)`）改小或改為自我重排的迴圈；因單飛守衛 `if (commands) return commands`（`app.ts:99`），long-poll 回來後立刻再撈，達到近即時。

### 5. 並發安全複核（不新增鎖，只確認既有保護足夠）
- `Worker.deliver` 已用 `claimJob()` 原子認領（`engine.ts:425`）、逐 part 重查 `getBatch()?.state !== 'sealed'`（`engine.ts:433`）、`store.transaction()` 包 `finishStep`（`engine.ts:459`）。
- 指令的狀態變更（approve/skip/cancel）都走 `store.transaction()`（`engine.ts:206/231/250`）。
- 因此指令車道與重工作車道即使同時觸及同一批次，SQLite 交易與狀態守衛會讓過時動作安全 no-op，不會資料損壞。此步驟只做程式碼複核與必要的防禦性狀態重查補強，不改資料模型。

### 6. 測試與驗證
- 新增/調整測試：
  - `SerialWork` 雙實例互不阻塞（control 任務不等 heavy 任務）。
  - long-poll 參數正確傳遞。
  - approve callback 觸發背景 worker.run 且立即回覆、不阻塞。
  - 既有 collectCycle / worker / engine 測試維持綠燈。
- 執行 `npm run verify`（TypeScript build + 全套測試）。此次 verify 也會一併驗證先前寫入但尚未編譯驗證的 review-notice 程式（types.ts/store.ts/engine.ts）與本次 t.co 修正（x.ts/http.ts/types.ts）。
- 遵守約束：只實作與跑 build/測試，不啟動服務、不對真實 X/Telegram/下游發送。

## 風險與取捨
- 拆車道後，理論上收集中的 worker.run 與指令觸發的 worker.run 可能重疊 —— 但 `Worker.run` 的單飛守衛（`active` promise）已保證同時只有一個 deliver 迴圈，第二個呼叫併入同一 promise，安全。
- long-poll 讓一條 HTTP 連線維持最多 25s；需確認 transport 的逾時設定不會把正常的 long-poll 當成逾時錯誤（步驟 4 一併處理）。

## 不做
- 不改用 worker_threads / child_process（瓶頸是等待非 CPU；且 SQLite handle 與 Playwright 實例無法跨線程共享，複雜度高收益低）。
- 不改 SQLite 為非同步或換 DB。
- 不動 X 唯讀、X 發文手動的約束。
